[10번째 리눅스 글](/blog/10-inode별-세개/)로 inode에 대해 알아보았다.
inode라는 파일의 실체를 우리가 아는 이름을 붙여 접근할 수 있게 만드는 것이 링크이다.

# 링크
> inode(파일의 메타데이터이자 실체)와 디렉토리 엔트리를 연결하는 것을 의미한다.

# 디렉토리 엔트리?
> 이름과 inode 번호를 매핑한 테이블이다.

디렉토리 엔트리와 inode 번호를 매핑하면, 파일명을 통해 inode에 접근할 수 있게 된다. 하나의 inode에 여러 개의 디렉토리 엔트리를 연결해 바로가기를 만들 수 있다.

# 하드링크 (Hard Link)
> 같은 inode 번호를 가리키는 또 다른 디렉토리 엔트리를 만드는 것이다.
> (바로가기 만들기)
### 하드링크 만들기 `ln`
```bash
ln 원본 링크이름
```
- inode의 link count가 1증가한다.
- 원본과 링크는 완전히 동등하다.
	- 누가 링크, 누가 원본 이런 개념이 없다.
- 파일 삭제는 사실 아래와 같이 동작한다.
	- `unlink()`를 호출 -> 디렉토리 엔트리 제거 -> link count 1 감소.
	- count=0이 되면 실제 데이터 블록이 해제된다.
- 하드링크는 같은 **파일 시스템 내에서만 가능**하다.
- 디렉토리에 대해서는 하드링크를 만들 수 없다.
	- 순환 구조가 생길 수 있기 때문이다.

# 심볼릭 링크 (Symbolic Link, Soft Link)
> 별도의 inode를 가진 **별도의 파일**. 그 안에 원본 경로(path) 문자열이 저장된다.
### 심볼릭 링크 만들기
```bash
ln -s 원본 링크이름
```
- 원본 inode를 직접 가리키지 않는다. 경로를 가리킨다.
- 원본이 삭제되면 심볼릭 링크는 깨진 링크가 된다.
	- dangling link
	- `ls -l`에서 빨간색 깜빡임으로 표시되기도 함.
- 파일 시스템의 경계를 넘을 수 있다.
- 디렉토리에 대해서 심볼릭 링크를 만들 수 있다.
- `ls -li`를 통해 원본과 링크의 inode 번호가 다른 것을 확인할 수 있다.
- `ls -l` 결과에 파일 권한 맨 앞에 파일 타입 자리에 `l`로 표시된다.

# 심볼릭 링크 vs 바인드 마운트
다른 경로를 통해 같은 내용에 접근하는 길을 만든다는 점에서 심볼릭 링크와 [바인드 마운트](/blog/5-마운트와-바인드/)는 꽤 비슷해보인다.

하지만 근본적인 동작부터 차이가 있다.

### 동작 계층
- 심볼릭 링크: 파일 시스템 상의 파일
- 바인드 마운트: VFS 마운트 테이블의 엔트리

> [!info] VFS(Virtual File System)
> 리눅스 커널이 서로 다른 파일 시스템(ext4, XFS, Btrfs, NFS, overlayfs 등)을 동일한 방식으로 다루기 위해 두는 추상화 계층이다. 각 파일 시스템이 각각의 함수들을 구현하여 VFS에 등록해 사용하는 공통 인터페이스 역할을 한다.

### 파일 타입이 `l`인가 `d`인가
`ls -l`로 살펴보면 심볼릭 링크는 `l`로 표시되고, 바인드 마운트는 그냥 평범한 디렉토리(`d`)로 보인다.

### 해석 시점
- 심볼릭 링크: pathname lookup 중 커널이 문자열을 읽고 재탐색한다.
	- 커널이 파일을 열 때마다 경로 문자열을 다시 읽고, 경로를 재탐색한다!
- 바인드 마운트: mount 시점에 동일 서브트리로 연결된다.
	- 마운트 트리 자체를 조작하므로 source와 target이 완전히 동일한 inode를 가리키게 된다.
	- 컨테이너 런타임이 이미지 레이어를 컨테이너의 rootfs에 올릴 때 바인드 마운트를 쓴다.
### 영속성
- 심볼릭 링크: 디스크에 데이터로 존재한다.
	- 재부팅 후에도 유지된다.
- 바인드 마운트: 커널 런타임 상태에 유지된다.
	- 재부팅하는 경우, 사라진다.
