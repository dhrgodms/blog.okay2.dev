> 자기 자신에게 바인드 마운트 하는 것을 의미한다.

어제 회사에서 마주친 문제를 곰곰이 생각해보다가 바인드 마운트와 양상이 다르다는 생각에 마운트에 대해 한 번 더 알아보게 되었다.

바인드 마운트를 하는 경우에 디렉토리 내부에 있는 내용물이 마운트된 source 내용으로 덮어씌워져 주로 안보이는데, 내가 살펴본 컴퓨터의 경우 디렉토리 내부 내용물이 잘 보였다. 그럼 그냥 바인드 마운트가 아니라는 것!

---
# 1. 셀프 바인드 마운트인지 확인해보기

### 마운트 포인트 확인하기
`lsblk`를 통해 어떤 디바이스에 어디 디렉토리가 마운트되어있는지 확인할 수 있다. 내가 본 결과는 아래와 같았다.
```bash
testuser@testuser:~> lsblk
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
sda           8:0    0   100G  0 disk 
├─sda1        8:1    0    76G  0 part /mnt/usb
│                                     /mnt/testuser
│                                     /
├─sda2        8:2    0    20G  0 part 
│ └─oracle  253:0    0    20G  0 crypt /home/oracle
└─sda3        8:3    0     4G  0 part [SWAP]
sr0          11:0    1  1024M  0 rom
```
뭐지 이것은.. `lsblk`의 `MOUNTPOINTS`(복수형) 컬럼은 원래 한 디바이스에 마운트포인트가 여러 개면 항상 이렇게 멀티라인으로 나열해서 보여준다. 즉 이 결과만으로는 셀프 바인드 마운트인지 아닌지 판단할 수 없고, sda1 파티션 아래에 `/mnt/usb`, `/mnt/testuser` 둘 다 마운트되어 있다는 사실만 알 수 있다. 진짜 판별은 아래 `findmnt`로 해야 한다.

### 어디에 뭐가 마운트되어있나 확인하기

```bash
findmnt -o TARGET,SOURCE,FSTYPE
```
를 확인해보면, 내 자신을 재마운트한 경우라면 target과 source가 아래와 같이 동일하다.

```
testuser@testuser:~> findmnt | grep sda1
/                          /dev/sda1             ext4
├─/mnt/testuser            /dev/sda1[/mnt/testuser] ext4
└─/mnt/usb                 /dev/sda1[/mnt/usb]   ext4
```

이것을 보면 /dev/sda1에 이미 포함되어 있던 디렉토리인 /mnt/testuser가 자신에게 바인드 마운트한 형태임을 볼 수 있다.


아마 아래와 같은 명령어로 마운트 했을 것이다.
```
mount --bind /mnt/testuser /mnt/testuser
```
> [!seealso] docker 컨테이너에서 셀프 바인드마운트를 하는 것은 `findmnt`로 조회했을 때 `SOURCE`가 `overlay`로 나온다. 위 결과물은 실제 vm에서 볼 수 있다.

# 2. 셀프 바인드 마운트의 목적
- 특정 디렉토리를 별도의 마운트 지점으로 만들어야 사용할 수 있는 옵션들이 있다.
	- 컨테이너, chroot 격리 시 필수
- 특정 폴더에만 격리된 파일 시스템 옵션을 부여할 수 있다.
	- 바이러스/스크립트를 특정 디렉토리 안에서만 실행금지(`noexec`)하거나 `nosuid` 옵션을 걸고 싶을 때
	- `nosuid`: 파일 시스템 마운트 시 SetUID 및 SetGID 동작을 무시하도록 강제하는 옵션
- SELinux/접근 제어 레이블 분리를 위하여 사용할 수도 있다.


## SELinux와 접근 제어 레이블?
### SELinux
> 리눅스 커널에 추가된 강제 접근 제어(Mandatory Access Control) 보안 모듈

- 미국 국가안보국이 개발해서 리눅스 커널에 추가했다.
- 기존 방식 (임의 접근 제어; DAC)
	- root 계정 중심 `rwxrwxrwx`
	- 관리자 권한 탈취 시 취약해짐
- SELinux 방식 (강제 접근 제어; MAC)
	- root 권한이라도 커널에 등록되지 않은 정책의 행동은 차단한다.
- 일반 리눅스 계정과 별개인 SELinux 사용자 계정을 이용한다.

### 접근 제어 레이블
SELinux가 시스템의 모든 프로세스, 파일, 디렉토리, 포트, 네트워크 장치에 이름표(접근제어레이블)를 붙여서 관리한다.
- 어떤 타입의 프로세스가 어떤 타입의 파일에 접근하려 하는지 매번 SELinux Policy(일종의 테이블)과 대조한다.
- SELinux를 이용하는 경우, 특정 프로세스가 777의 권한이 있더라도 SELinux Policy에 허용 룰이 없다면 커널 레벨에서 Permission Denied 처리된다.
- SELinux를 사용할 때 볼 수 있는 `ls -Z` 결과
```bash
system_u:object_r:httpd_sys_content_t:s0
```
- system_u: 사용자(SELinux 사용자)
	- 일반 리눅스 계정 `unconfined_u`
- object_r: 역할(파일)
	- 사용자 `user_r`
- httpd_sys_content_t: 타입/도메인
	- 이 파일/프로세스의 용도를 정의한다.
	- `[서비스/프로그램명]_[용도/상세]_[접미사]` 구조
	- `_t` = 타입이라는 의미의 접미사
	- `httpd_sys_content_t`
		- httpd 서비스가 sys (전역)에서 content(정적 콘텐츠)를 보여주기 위한 용도로 쓰이는 t(타입)
- s0: 레벨
	- 다중 보안 레벨 등급
	- 주로 컨테이너 격리에 사용한다.

# 3. 셀프 바인드마운트 목적 찾기
1. SELinux를 이용하는지 확인한다.
	- 모든 리눅스가 SELinux를 이용하진 않지만, RHEL 계열은 기본적으로 활성화되어있다. 
	- 데비안/우분투 계열은 기본 미사용
	- `getenforce`로 SELinux 보안 정책을 사용 중인지 알 수 있다.
2. 커널의 마운트 정보 파일 + SELinux 레이블 조회 명령어 살펴보기
	- `/proc/self/mountinfo` 마운트 정보 파일
	- 마운트 정보를 담은 row 확인 가능
	- 여기에서 /mnt/testuser 이거나 /mnt/usb인 문자열 찾기
		- `grep -E '/mnt/testuser|/mnt/usb'`
			- `-E`: 확장 정규표현식 사용하겠다는 뜻 (특수문자 이스케이프 안해줘도 된다)
```bash
testuser@testuser:~> cat /proc/self/mountinfo | grep -E '/mnt/testuser|/mnt/usb'

379 69 8:1 /mnt/testuser /mnt/testuser rw,relatime shared:1 - ext4 /dev/sda1 rw,seclabel
501 69 8:1 /mnt/usb /mnt/usb rw,relatime shared:1 - ext4 /dev/sda1 rw,seclabel
```
- `shared:1`: 외부 네임스페이스와 마운트 이벤트를 공유하기 위한 목적이다.
	- 외부의 변경사항만 전달받는 목적이면 `master:x`
	- 다른 곳으로 복제 마운트되는 것을 방지하는 목적이면 `unbindable`
3. 특정 파일 시스템 옵션 격리 여부 확인
- 따로 실행 제한이나 보안 플래그가 있을 수 있다.

```bash
testuser@testuser:~> findmnt -o TARGET,SOURCE,OPTIONS | grep -E '/$|/mnt/testuser|/mnt/usb'
├─/mnt/testuser               /dev/sda1[/mnt/testuser] rw,relatime,seclabel
└─/mnt/usb                    /dev/sda1[/mnt/usb]      rw,relatime,seclabel
testuser@testuser:~> ls -Zd /mnt /mnt/testuser /mnt/usb
system_u:object_r:mnt_t:s0 /mnt unconfined_u:object_r:mnt_t:s0 /mnt/testuser unconfined_u:object_r:mnt_t:s0 /mnt/usb
```
근데 내가 살펴보던 컴퓨터는 놀랍게도...옵션도 적용돼있지않고 SELinux를 적용하는 사용자 계정도 아니었다.
보안옵션 격리 목적도 아니고, SELinux 정책 분리 목적도 아니다.

### 목적 추측
- 아마 특정 데몬이 내부적으로 `mountpoint` 를 확인하기 때문인 듯
	- **이 경로가 별도의 마운트 지점으로 잡혀있는지 확인**
	- 일반 폴더는 마운트 포인트로 인식되지 않기 때문이다.
- chroot/컨테이너 네임스페이스 격리 공유를 위한 목적일수도
	- 다른 격리 환경에 해당 폴더만 **마운트 이벤트를 전파하기 위해** 마운트 지점으로 승격시켜둔 형태
	- 일반 디렉터리는 단독으로 `shared` 속성을 가질 수 없고, 오직 **마운트 포인트로 등록된 디렉터리만 전파 속성을 가질 수 있다**.
	- `/mnt/testuser` 아래에 또다른 볼륨(USB 등)을 마운트 했을 때, 이 디렉터리를 공유하는 다른 네임스페이스 내부에도 그 마운트 결과가 실시간으로 반영되기 위함이다.
	- 어떤 프로세스가 이 디렉토리를 쓰고 있는지 확인해보면 알 수 있다. (다른 마운트 네임스페이스에서 쓰는 경우도 있음)
