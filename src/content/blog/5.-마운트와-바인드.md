# 1. mount
> 디스크 파티션, USB, 네트워크 드라이브, **심지어 다른 위치의 디렉토리**까지도 특정 경로에 연결해서 그 경로를 통해 접근할 수 있게 하는 기능

- 리눅스는 모든 걸 파일 시스템 트리 안에서 다룰 수 있다.
- 마운트 지점에 있던 원래 내용은 마운트 되는 동안 가려진다.
	- 언마운트하면 다시 보인다.
- `mount` 명령어를 통해 현재 마운트된 목록을 조회하거나 마운트 기능을 사용할 수 있다.
- 부팅 시 자동 마운트하기: `/etc/fstab`에 등록
- 주로 디바이스 -> 디렉토리를 연결한다.
```bash
mount [디바이스] [디렉토리]
mount /dev/sdb1 /mnt/usb
```
위와 같이 사용하면, `/mnt/usb` 경로로 `/dev/sdb1` 블록 디바이스를 연결하게 된다.
- `/mnt/usb` 경로 아래 들어가면 `/dev/sdb1` 파일시스템을 볼 수 있게 된다.

# 2. bind-mount
> 일반 마운트는 디바이스 -> 디렉토리
> 바인드 마운트는 **디렉토리 -> 디렉토리** 의 연결이다.

- 새로운 파일 시스템을 연결하는 것이 아닌, 이미 존재하는 디렉토리를 다른 경로에서도 똑같이 보이게 만드는 것이다.
```bash
mount --bind /home/user/project /var/www/project
```
위와 같이 사용하면, `/var/www/project`에서 보이는 내용은 `/home/user/project`의 내용과 완전히 동일하다.


> [!seealso] 리눅스에서의 또다른 바인드(bind)
> - 마운트 바인드: 디렉토리(inode)를 다른 경로에 연결
> - 소켓 바인드: 소켓을 IP/포트에 결합

## 심볼릭 링크와 바인드 마운트의 차이
### 동작 방식
- 심볼릭 링크
	- 경로를 가리키는 참조
- **바인드 마운트**
	- 커널 레벨에서 **같은 inode**를 다른 경로에 노출

### 특정 프로그램이 어떻게 인식하는가
- 심볼릭 링크
	- 일부 프로그램으로부터 가리키는 경로와는 구별되는 취급을 받는다.
- 바인드 마운트
	- 진짜 디렉토리처럼 동작하기 때문에 완전히 동일하게 취급 받는다.

# 3. 바인드 마운트, 그리고 chroot/컨테이너의 원리
> 컨테이너는 사실 호스트의 파일 시스템 내에 독립적으로 격리된 파일 시스템이다.

## 컨테이너의 격리
- 컨테이너(docker 등)는 리눅스의 **네임스페이스** 기능으로 격리를 만든다. 
- **마운트 네임스페이스**(mount namespace) 이 핵심!
	- 프로세스가 보는 파일시스템 트리는 호스트가 보는 파일 시스템 트리와 다르게 만들 수 있다.
	- 컨테이너 안에서 `ls /` 을 실행하면, 호스트의 `/`가 아닌 **이미지에서 만든 독립된 루트 파일 시스템**이 보인다. 컨테이너는 이 안에 생태계가 있는 것이다.
- 그런데, 이 컨테이너의 파일 시스템은 이미지로부터 만들어진다.
	- 만약에 이 컨테이너가 죽으면? 그 안에 변경된 내용도 사라진다!
	- ***근데 컨테이너가 죽어도...데이터가 남아있어야 한다면???***
	- 이때, 바인드 마운트를 사용하는 것!


> [!note] 컨테이너의 쓰기 동작
> 컨테이너는 이미지의 레이어 위에 쓰기 가능한 임시 레이어를 얹어서 동작한다. 임시 레이어는 컨테이너와 생사를 함께 하므로 컨테이너가 죽으면 임시 레이어도 함께 사라지게 되는 것이다.

## 컨테이너에서의 바인드 마운트

#### 바인드 마운트가 필요할 때
- 컨테이너가 죽어도 DB 파일과 같은 데이터가 남아 있어야 할 때
- 호스트에서 코드를 수정하면 컨테이너 안에서도 반영되어야 할 때
- 호스트의 설정 파일을 컨테이너에 넘겨줘야 할 때
등등..

이미지로 만든 파일 시스템을 다루는 컨테이너 내부와 호스트를 연결해야될 때 바인드 마운트를 사용할 수 있다.

간단하게 도커를 구동하는 명령어를 통해 이해해보자.
```bash
docker run -v /host/data:/app/data abcimage
```
이 명령어의 동작 방식은 다음과 같다.
- 새 마운트 네임스페이스를 만들어서 컨테이너의 루트 파일시스템을 구성한다.
- `/app/data`라는 경로에 호스트의 `/host/data`를 바인드 마운트 한다.
	- `/app/data`와 `/host/data`와 같은 inode를 가리키게 된다. 그냥 같은 파일인 거임.


### 왜 복사하는 방식이 아니고, 다른 경로에 동일한 inode를 가리키게 만드는걸까?
- 호스트에서 수정했을 때, 컨테이너 안에 즉시 반영됨
- 컨테이너 안에서 어떤 내용을 쓰면, 컨테이너가 죽어도 호스트에 남아있음

이런 바인드 마운트의 특징은 도커의 **볼륨(volume)** 의 개념을 구현하는 방법으로도 쓰이게 되었다.

## 볼륨은 뭔데? - 여기에서는 Named Volume
> Docker가 관리하는 전용 영역으로, 컨테이너의 생명 주기와 무관하게 컨테이너 밖(호스트)에 실제 데이터를 저장하는 메커니즘이다.
> 
> - 호스트에서 직접 접근하기 어렵다. Docker가 알아서 관리해준다.
> - 같은 마운트를 활용하지만 볼륨은 사용자가 직접 접근해서 이것저것 하기 위한 용도는 아니다.
> - 주로 프로덕션 DB 데이터 저장을 위해 사용한다.
> - `/var/lib/docker/volumes/...`경로에 저장된다.
> - `-v [볼륨명]:/container/path` 방식으로 사용한다.

- 그에 비해 바인드 마운트는...
	- 호스트의 아무 경로나 지정 가능하다.
	- 호스트에서 그냥 그 경로로 가면 접근하는거임.
	- 주로 개발 중 코드 마운트, 설정 파일 주입 등을 위해 사용한다.
	- 호스트 경로 구조에 의존적이다.
	- `-v [호스트경로]:/container/path` 방식으로 사용한다.

## 좁은 의미에서의 볼륨, 넓은 의미에서의 볼륨
- 좁은 의미: docker가 관리하는 named volume을 의미
- 넓은 의미: bind mount, named volume, tmpfs를 통칭
	- tmpfs: 디스크가 아니라 RAM에 저장하고, 컨테이너 종료 시 사라진다.

# 4. chroot
> 프로세스가 보는 파일 시스템의 루트`/`를 특정 디렉토리로 바꾸는 기능이다.
> change root의 줄임말이다.

```bash
chroot /abc/directory /bin/bash
```
와 같이 실행하면 이 안에서 실행되는 bash에서의 루트 디렉토리`/`는 `/abc/directory`가 된다.
- 바깥 디렉토리는 볼 수 없다. (원칙적으로는 그렇다.)
```
실제 파일시스템:
/
├── home/
├── some/
│   └── directory/     ← chroot 대상
│       ├── bin/
│       ├── etc/
│       └── lib/
└── var/

chroot 된 프로세스가 보는 세상:
/                       ← 사실은 /some/directory
├── bin/
├── etc/
└── lib/
(home/, var/ 등은 존재 자체를 모름)
```

### chroot 사용 목적
- 디렉토리 안에 서비스를 가두고, 시스템 전체에 영향을 주지 못하도록 한다.
- 다른 배포판, 시스템의 테스트/복구 환경을 구성하기 위해 실제 부팅 없이 디렉토리 안에서 실행할 수 있도록 한다.
- 필요한 것만 있는 빌드 환경을 구성할 수 있다.
- 컨테이너의 원조 아이디어라고 할 수도 있다!
- chroot도 `chroot()`라는 시스템 콜로 구현된다. 바인드 마운트 아님.

아래 명령어는 
① `/dev` 를 `/chroot-env/dev` 와 연결하고 
② `chroot`를 통해 실행되는 bash에서는 `/chroot-dev`가 루트 디렉토리`/`가 되도록 한다.
```bash
mount --bind /dev /chroot-env/dev
chroot /chroot-env /bin/bash
```

# 5. 한마디로 정리하면..
- mount는 주로 디바이스와 디렉토리를 연결한다.
- bind-mount는 주로 디렉토리와 디렉토리를 연결한다.
- volume는 컨테이너에서 바인드 마운트 원리를 이용해 컨테이너 생명주기와 독립된 데이터를 저장할 수 있게 한다.
- chroot는 특정 디렉토리를 루트 디렉토리로 착각하도록 만드는 것이다.
